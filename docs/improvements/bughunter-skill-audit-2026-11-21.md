# Claude-BugHunter Skill Audit & Single-Skill Experiment, 21 November 2026

Read-only security and concurrency audit of `repo/satori` comparing four passes using skills from `elementalsouls/Claude-BugHunter`:

1. **Pass 1 — No skill files read (general audit):** Audited obvious trust boundaries from memory/README only.
2. **Pass 2 — 5 skills in one pass (`hunt-rag-vector`, `hunt-llm-ai`, `hunt-nodejs`, `hunt-cicd`, `hunt-race-condition`):** Spread context across 5 domains in a single turn.
3. **Pass 3 — 1 skill deep dive (`hunt-race-condition` only):** Focused exclusively on check-then-act, lock mutual exclusion, async TOCTOU, and concurrent staging/cleanup paths.
4. **Pass 4 — 1 skill deep dive (`hunt-nodejs` only):** Focused exclusively on Node.js runtime sinks (`fs`, `child_process`, symlinks, `tsconfig`/compiler FS callbacks, glob traversal, dynamic loaders, env/config quoting).

## Experiment takeaway: 5 skills at once vs. 1 skill per pass

Running 5 skills in one pass diluted depth. It spread reads thinly across CI workflows, vector DB clients, rerankers, CLI installers, and MCP tools, catching mostly configuration/hygiene issues and missing deep runtime flaws.

Re-running **one skill per pass** consistently surfaced far higher-severity, codebase-specific defects that both earlier passes completely missed:
- **Pass 3 (`hunt-race-condition` only):** 5 deeper concurrency/locking bugs (`withOwnerLock`, unlocked `uninstall --purge`, `ensureModel` shared `.partial` race, unlocked `inspectManagedRuntimeLeases` deletion, `withRootKeyLock` stale-break TOCTOU).
- **Pass 4 (`hunt-nodejs` only):** 6 deeper Node.js runtime/filesystem bugs (out-of-root file reads & FIFO hang via TypeScript 7.1 `ts.API` FS layer, symlink-following arbitrary write via `satori.toml` in `satori install --profile`, unsafe `JSON.stringify` POSIX shell quoting in Claude Code `SessionStart` hook, unbounded `fs.globSync`/control-file reads in package ownership, missing runtime SHA-256 verification on extended CBM WASM + untimeouted Swift child process, and newline injection in `EnvManager.set`).

## Pass 3 — Single-Skill Deep Dive (`hunt-race-condition` only)

Focused solely on Satori's lock files, concurrent lifecycle transitions, and shared mutable state. Every finding below was missed in both Pass 1 and Pass 2.

| # | Severity | Area | Finding | Evidence | Impact | Recommended action |
|---|---|---|---|---|---|---|
| P3-1 | **High** | MCP / Runtime Owner Lock | `withOwnerLock` breaks mutual exclusion in three ways: (1) `if (shouldBreakOwnerLock(lockPath)) fs.unlinkSync(lockPath)` unlinks by path with **no inode check** — two contenders seeing a stale lock let the second contender delete the first contender's newly acquired live lock; (2) `finally` unconditionally calls `fs.unlinkSync(lockPath)` after `closeSync(fd)` without verifying `fstatSync(fd)` matches `lstatSync(lockPath)`, deleting a successor's active lock if broken/superseded; (3) `shouldBreakOwnerLock` checks only `processExists(pid)` with no `processStartTime`/`bootId` (PID-reuse blind spot), and a `writeFileSync` error leaks `fd` and an empty lock file. | `packages/mcp/src/core/runtime-owner.ts:766–826` | `withOwnerLock` is the sole mutual-exclusion primitive for `owners.json`, `checkMutation`, and `withSoleRegisteredOwnerLock` / `withRuntimeOwnerMaintenanceLock` (the destructive GC sole-owner gate). A lost-lock race can let destructive storage GC run concurrently with a registering runtime or allow conflicting runtimes to mutate indexes simultaneously. | Replace with the atomic hard-link publication + hard-link stale-claim pattern from `shared-runtime-lifecycle.ts`, include `bootId` + `processStartTime`, verify `fstatSync(fd)` identity before unlink in `finally`, and clean up on `writeFileSync` failure. |
| P3-2 | **High / Medium-High** | CLI / Uninstall & Purge | `executeInstallCommand` acquires `acquireManagedRuntimeMutationLock({ homeDir })` only inside `if (command.kind === "install")`. `satori uninstall` and `satori uninstall --purge` never acquire the mutation lock before mutating client configs or recursively deleting `~/.satori` / `SATORI_STATE_ROOT`. | `packages/cli/src/install.ts:135–141, 415–425` | A concurrent `satori uninstall --purge` races directly with `satori install`, `satori upgrade`, or `satori reranker`, risking partial deletion of a newly installed runtime/model cache or recreating `~/.satori` mid-purge. | Acquire `acquireManagedRuntimeMutationLock` for non-dry-run `uninstall` (and hold or fence cleanly before `purgeSatoriData` removes the runtime store). |
| P3-3 | **Medium** | CLI / Model Store | `ensureModel` writes all downloads into one shared, unlocked deterministic staging directory (`.${path.basename(modelDirectory)}.partial`), yet line 544 explicitly assumes concurrent installers can race to publish the same revision (`// Another installer may have published the same revision first.`). It also runs `fs.rmSync(modelDirectory, { recursive: true, force: true })` on failed verification without a lock or atomic detach. | `packages/cli/src/model-store.ts:353, 435–457, 544–549` | Any concurrent caller of `ensureModel` opens the same staged file in `"a"`/`"w"` mode simultaneously, interleaving bytes, tripping false `integrity` errors that unlink the peer's active file, or renaming `staging` while the peer still holds an open write fd. | Either serialize `ensureModel` per model directory with a lock file or stage into a unique per-attempt directory (`.partial.<pid>.<uuid>`) when another attempt is active, and detach-rename corrupt `modelDirectory` before removal. |
| P3-4 | **Medium** | CLI / Lease Inspection | `inspectManagedRuntimeLeases` calls `collectLeaseProtectedRoots` **without holding `LEASE_LOCK_FILE`**, even though `collectLeaseProtectedRoots` destructively deletes lease files (`fs.rmSync(leasePath, { force: true })`) with no inode check. | `packages/cli/src/managed-runtime-store.ts:265–290, 553–570` | A read-only inspection API has destructive side effects and races with concurrent launcher lease creation and `pruneManagedRuntimeStore`. | Separate read-only lease inspection from stale-lease cleanup, and perform cleanup only under `LEASE_LOCK_FILE` with inode verification. |
| P3-5 | **Low–Medium** | Core / Mutation Lock | `withRootKeyLock` captures `existingStat = fs.lstatSync(lockPath)`, then `shouldBreakLock` re-reads `lockPath` by path (not via an open fd), and `removeLockIfUnchanged` checks `lstatSync` then `unlinkSync` without holding the fd or a hard-link claim — leaving a narrow TOCTOU/inode-reuse window that `shared-runtime-lifecycle.ts:144–191` (`removeStaleLockWithoutReplacingNewOwner`) already solved elsewhere in this repo. | `packages/core/src/generation/root-mutation-coordinator.ts:792–840` | Under rapid lock turnover + stale recovery, a contender can unlink a newly created replacement lock if the path changes between `lstatSync` and `unlinkSync`. | Hold an open fd during inspection (like `managed-runtime-store.ts:508–531`) or adopt the hard-link claim protocol (`fs.linkSync` + `nlink === 2`) from `shared-runtime-lifecycle.ts`. |

## Pass 4 — Single-Skill Deep Dive (`hunt-nodejs` only)
